新產品方向：單一自營商家的門市購物流程。買方送出要求，系統核價並保留帳面數量，門市實際揀貨後確認供應。第一版先跑通人工處理，不做支付、配送或售後。

使用者以門市即時購物 app 作為體驗參考。以下記錄本專案已選的規則，不宣稱已查證或重現任何業者的完整制度；這次包含業務改變，不只是重構。

範圍已確認的選擇不代表什麼
經營模式與範圍單一商家、自營商品與庫存；第一版到人工揀貨、供應確認與結果查詢。不一次加入多賣家、分潤、支付（含模擬支付）、配送、退貨、退款或替代商品。
送單與供應分開送單成功代表系統已保存這次購買要求及受理結果；最終哪些商品能供應，等門市實際揀貨確認。不是送單當下就保證備齊，也不是背景再查一次 DB 庫存來代替人工揀貨。
先保留帳面庫存送單時對可售、價格核對成功且帳面足量的商品，先保留完整要求量，避免其他線上要求重複占用。不是購物車就先 hold；也不能消除帳面與現場差異。保留成功尚不等於供應保證。
同商品不減量要 5 件就必須備齊 5 件。帳面不足，該項不進待揀；現場只有 4 件，該項整項不供應，解除該項尚有效的保留。不先保留部分等補貨，不擅自改成 4 件，不替換商品，不自動候補或補單。
各商品分別判斷一項未進待揀或最後無法供應，不影響其他商品各自確認。原始要求、逐項結果與原因都保留。不是允許 DB 寫到一半；全部未進待揀或最後全部無法供應，也不能刪掉這次購買紀錄。
價格與名稱送單時由後端核對買方同意價；異價該項不進待揀，提供新價供重新決定。通過的商品保存送單當次名稱與單價，等待期間改價不影響本次。不信任任意 client 報價，不等揀貨才決定成交單價；最後只按確認供應內容與已固定單價計算，不重新套現價。
買方改單與取消送單成功後不提供買方自行修改或取消，並在送單前明確說明。不另外建立「開始揀貨前可取消」的窗口；門市回報缺貨是供應確認，不是買方部分取消。
人工處理與整筆取消第一版先提供可見的待處理要求，由門市處理或人工整筆取消、解除尚有效的保留。不代表門市任何階段都可取消；授權、可取消時機、已拿出商品如何回架仍待定。買方沒有因此取得取消權。
自動到期先跑通人工流程，第一版不做自動到期；未處理要求可能持續占住庫存，要能看見並人工處理。這是開發順序，不是永久不設期限；HTTP timeout 不能觸發自動釋放，也不先加到期 worker。
商品下架只停止新銷售；有既有要求或保留量仍可下架。舊紀錄、供應處理與解除保留不能被可售過濾隱藏。不抹除庫存、不自動取消既有要求。舊「保留量大於零就禁止下架」不再是目標需求。
買方停用保留「有 Active Order 的買方不能停用」的原則；資格檢查與送單／停用仍須協調。新增待揀與供應確認後，哪些階段算 Active Order 要重新定義，不能直接沿用「尚未 Cancel」當完整答案。
同次重試同一次送單有穩定身分，不重建、不重複保留，也不重新核價或嘗試被排除商品。原受理結果固定，目前進度則可往後更新。不能永遠只回待揀而讓買方看不到後續結果；歷史重播與進度查詢的 HTTP 形狀仍待定。刻意再買用新身分。
過載與待辦HTTP 等待與在途量有上限，未受理時明確拒絕；已受理的人工待辦必須持久化，重啟後仍可見。人工待辦不是無限 HTTP 等待；也不因需要保存待辦就必須先上 MQ。業務待辦容量上限尚未定。
高承載目標一般零售混合流量，另測有限熱門商品；分開量送單／帳面保留能力與門市供應完成速度。不把快速收進大量待辦當成同等供應能力；沒有量測就不宣稱 TPS、p99 或門市處理量。
本輪定案 · 2026-11-26

用定義拿掉不需要的分支，但不掩蓋真實故障

「以定義規避例外」在這裡的具體選擇，是不提供縮量、替代商品及買方送單後自行改單／取消。買方事前知道限制，系統就不必先建造所有可能的變更流程。仍需由後端限制操作，不能只把畫面按鈕藏起來。

現場缺貨是正常供應結果；重複操作、DB 故障、保留量錯帳與門市無法處理，仍要有正確且可見的處理方式。產品規則不能讓這些問題自動消失。

先做這個版本，之後有真需求再調整。現在不先決定所有狀態、資料表或未來流程，也不為將來可能變動先做可切換全部規則的框架。

新產品草案取代的假設：不再是「送單時就確定供應，所有結果一次完成」。現在是送單核價與保留、人工揀貨、後續供應確認；買方不能自行取消，門市仍有人工整筆取消。原草案「只保留最後成立商品」的資料模型與庫存公式也要重看；這些變更不回溯要求既有作業改成新產品。

還沒決定的部分，留到相應步驟再定

人工揀貨、先保留、同商品不減量、送單固定價、買方不能自行取消已定案。下面才是未決事項；實作某一步前先補齊它依賴的契約，不要求一次設計完整零售系統。

尚待討論

購買要求、待揀與最後供應內容，怎麼記錄與結束？

至少要分得清買方原本要求、送單受理結果、目前仍有效的保留，以及門市最後確認內容。哪些共用 Order／Order Line、Order 何時建立、狀態名稱、逐項回報或整批完成，尚未定案；本頁使用的「待揀」是業務描述，還不是已選的 enum。

供應確認後，保留繼續存在、轉為已售出或在某個完成動作結束，也還沒決定。不能因為第一版不做配送，就默認它永遠是未取消的持有量。

需要補齊的決定目前可確定的底線
送單身分的 caller／買方範圍、同身分異內容同一意圖才能重播，不洩露別人的結果。建議異內容視為衝突，不重新執行；共用機器帳號還不是買方資源授權。
結果保存期限與過期回應不能默默清掉去重紀錄，再把舊重試當新購買。已保存的價格與初次排除理由不因補貨、改價、揀貨或取消而被改寫。
受理／全未進待揀／供應結果的 HTTP 契約分清歷史受理結果與目前進度，包含逐項原因、查詢位置、重播、Location 與技術失敗；不能被 CreatedResponse 只有 id 限制。本輪不先指定 200／201／202 等完整答案。
門市作業與授權要能看待辦、回報供應及人工整筆取消；誰能操作、是否認領、可取消階段、原因與回報粒度待定。重複回報不能多還量；互相衝突的回報與取消，也不能各自當作成功。
帳面差異與商品回架解除保留不等於補貨或盤點校正。缺貨怎麼修正帳、已拿出的商品何時回架與再次可售，需另定；不能只把數量加回去就宣稱現場有貨。
確認後生命週期與 Active Order供應確認後如何完成、保留如何結束，以及待揀／部分供應／全未供應／門市取消各階段是否阻擋買方停用，要一起定義。
待辦容量與日後自動到期第一版不做自動到期；需接受未處理就持續占量的代價。是否限制業務待辦量、未來期限與揀貨競爭，之後再決定，不默加逾時釋放。
新專案放置與版本管理目的地已確認為pxgo-clone；先交文件，再於新session實作。後端先做，前端／E2E日後同repo加入；目錄細節與新CI依工程階段落實。來源兩個repo與上下游CI保留。
初始資料與庫存管理先以單一庫存池分析，補貨／盤點權限待定。不預設搬舊資料，也不授權清庫；若日後選擇匯入，未知舊價不能假造，舊 reserved 需另驗。
數字化容量／延遲目標先固定環境與負載建立基準；系統吞吐與人工處理速度分開，不編造比例、TPS 或延遲保證。

從「哪些知識一起改」找責任

一起執行不等於一定屬於同一 module；跨時間也不代表一定跨服務。要找的是：改一條規則時，誰必須理解同一份知識，哪些 caller 不該被迫跟著改。

變化誰要理解規則協作者只需要知道不該被迫一起改
商品改價／改名商品販售管理現在名稱、權威價格與版本；接單在送單時核對並保存本次價格／名稱。該項能否依買方同意價進待揀，以及要保存的當次資料。原受理結果、待揀單價、歷史供應內容與庫存加減。揀貨不重新套現價。
停止販售商品販售限制新要求。新送單不可售；既有保留與處理紀錄仍存在。舊內容查詢、門市供應確認與解除保留，不必先重新上架。
補貨／盤點校正庫存區分補貨、帳面差異與解除保留。新的帳面可用量與受控調整；具體作業仍待定。已固定價格、先前排除原因。補貨不讓同次重試重新排隊。
同商品必須備齊接單與門市確認遵守全量或零供應；不足理由與原要求留下。庫存只按受保護的數量保留或解除，不自行選縮量政策。認證、HTTP 傳輸、商品介紹；不為一種已選政策造通用 engine。
回應遺失後重試接單保存穩定身分與初次受理答案；查詢可讀後續進度。已受理就回到同一份要求，不重建、不重新保留。現在價格、補貨、停售與揀貨進度不改寫第一次判斷。
門市回報備不齊揀貨／供應確認理解現場結果，保留原要求與失敗原因。解除該項尚有效保留；差異校正與再次可售依另定規則。買方取消權、送單固定價；不把正常缺貨當整個系統失敗。
門市整筆取消接單流程確認權限與可取消階段，協調尚有效的保留。庫存只解除這次要求仍持有的數量，不讓任意 caller 多還。當前售價、可售清單；不因此提供買方取消窗口。
買方停用條件買方資格能力與接單共同定義哪些處理階段算 Active Order。新送單與停用遵守同一守門方式。商品定價與庫存算式；不能為無環依賴圖刪掉真業務限制。
之後加入推播／簡訊流程保存已提交進度，通知負責投遞。哪個事實已發生，不必理解鎖序；第一版至少能查到結果。不把寄送等待塞進 DB 交易，目前不預選通知管道或可靠投遞框架。
判斷方法

一次操作內一起保存；人工等待前後分開保存

送單受理結果、固定價格與帳面保留不能各自成功一半。後續門市回報時，供應結果與必要保留變動也要一起保存。但它們之間隔著人工揀貨，不能塞進同一個長交易。

現在商品如何展示、原始要求保存什麼、門市如何確認、庫存如何安全計量，改變的原因不同，不應永遠共用會變動的 Product DTO。這是目前用例下的責任假說，新增真用例時再檢驗，不先替所有未來功能造框架。

責任候選，不是一個能力就拆一個服務

module 有 interface 與 implementation。interface 包含 caller 必須知道的規則、等待、錯誤與交易條件，不只是 Java 方法。本輪增加人工流程，但尚未批准新的 package、資料表或部署。

候選責任擁有的知識對外有用的 interface不應帶進來的東西
接單與處理進度原始購買要求、送單身分／去重、受理結果、固定價／名稱、進度查詢及門市取消的協調。送出一次要求、查原受理結果與目前進度；受授權的門市依流程整筆取消。讓買方任意改狀態、操作正反向庫存方法；把收到要求宣稱成供應保證。
揀貨／供應確認門市待辦、實際備齊與否、全量或零供應、缺貨原因，以及與取消的互斥。查看待辦並回報供應結果，不要求操作人員知道 DB 計量細節。重算現價、自動縮量、默加付款配送流程；目前不先定認領或逐件掃描制度。
商品販售目前名稱、權威價格、是否接受新要求及一致版本。查現在販售資訊，參與送單當下可售／價格核對。改寫舊單價格、支配既有保留的存在性或揀貨結束。
庫存帳面可用量、有效保留、條件更新、解除保留、鎖序與不變量。安全保留完整要求量、解除已證明持有的數量；正常不足回可判斷結果。把帳面量當現場保證，或把解除保留當補貨／盤點修正。再次可售與差異處理要依未來選定規則。
責任先清楚，組織方式之後定

揀貨可以先在接單 module 內；買方資格也不必膨脹成會員系統

第一版需要簡單買方資料、送單資格與停用限制。可先作本地支援能力；停用要問接單進度，新送單也要受資格限制，可由中立 use case 組合，避免兩邊互碰 Repository。

接單、揀貨與庫存可以在同一個較大 module 內分工。若拆開後 caller 仍得學完整流程與每個數量細節，先留在 implementation 也合理。不強制一個能力一個 interface、一個 package 或一個服務。

送單受理紀錄、目前進度與供應結果有不同用途，不代表每種都要新建一張表或一個微服務。下一輪先決定資料含義與狀態，再決定實體模型。

送單固定價，揀貨確認供應

先保留買方原始要求，再記送單時的判斷與後續供應結果。不能把缺貨商品刪掉，只剩最後商品卻無法解釋原本買了什麼。

第一版流程

先跑通人工處理，不一次設計完整營運

  1. 買方送出要求

    事前說明不足整項不供應、送單後不能自行改單或取消。後端驗格式、認證與授權，依穩定身分辨認同一次購買。

  2. 核價並保留帳面數量

    核對買方資格、可售與確認價。通過且帳面足量的商品保存送單名稱／單價，保留完整要求量；異價、不可售或不足的商品留下逐項原因，不進待揀。受理紀錄、去重與保留同一次短交易提交。

  3. 門市實際揀貨

    已受理要求是可持久保存的待辦。等待人員處理時不開著 DB 交易、不持有資料列鎖；第一版不自動到期，需能人工處理或整筆取消。

  4. 回報供應結果

    每個商品必須備齊要求量才供應；不足整項不供應，解除該項尚有效保留。其他商品獨立，單價沿用送單價。結果與必要保留變動用另一個短交易保存；回報粒度與確認後庫存生命週期尚待定。

  5. 買方查目前結果

    看得出還在等，或門市已完成哪些確認，也能看到未供應原因。第一版不預選推播或簡訊；查詢能力不能只停在初次送單回應。

例：買方送出牛奶 5 瓶、雞蛋 2 盒
送單時：
  牛奶每瓶 80 元，價格相符、帳面足量 → 固定 80 元，保留 5 瓶
  雞蛋價格相符、帳面足量 → 固定當次價格，保留 2 盒
  保存受理結果；此時尚未保證能供應

等待期間牛奶漲到 85 元，不改這次的 80 元
門市實際確認：
  牛奶只有 4 瓶 → 整項不供應，不改成 4 瓶，解除該項保留
  雞蛋備齊 2 盒 → 確認供應 2 盒，沿用送單價
  原始要求仍保留；牛奶帳面差異與再次可售另依規則處理
紀錄／情況需要保存什麼同次重試與查詢
原始購買要求買方要求的商品、數量、同意價與可辨認本次意圖的內容。不能因未進待揀、缺貨或門市取消而改寫。
初次送單受理結果哪些項目進待揀、固定名稱／單價與保留量，哪些被排除及原因。全部被排除也保存結果，不建立假的待揀工作。重試不重新判斷；補貨或改價後想再買，使用新身分。
目前處理進度仍待處理、已回報結果、門市整筆取消等可查資訊；具體狀態與模型仍待定。隨後續作業更新；不能用固定的初次回應代替目前進度。
供應確認結果每項全量或零供應與原因，全部無法供應也留下紀錄。使用已固定價格，不回查現價。同次重試不再排隊、不復活已排除商品、不重建保留。
門市整筆取消依將來選定的可取消階段，保存取消結果並解除尚有效保留；實體回架不是 DB 自動完成。原受理結果保留，目前進度反映取消，不因重播又恢復。
某次操作技術失敗該次尚未提交的結果與庫存變動一起 rollback；前一個已提交階段仍存在。提交結果不明先以穩定身分確認，不能盲目釋放或重新保留。

原來稱作「收據」的固定答案，現在只適合指初次受理紀錄，不是發票，也不是最後供應保證。POST 重播要回歷史答案或附目前進度、查詢如何呈現，仍待 HTTP 契約決定；不變的是同次送單不能重做一次。

正常不足與技術失敗分開：現有 applyStockDelta 不足就拋例外、整筆 rollback，不能只加 catch 假裝支援逐項結果。正常異價／不足應是可繼續判斷的結果；JPA constraint、連線、commit 失敗則是當次整體技術失敗，交易可能已 rollback-only。

人工流程跨時間，不必因此分散部署

以下是新產品的候選，先以單一後端 app＋Oracle 推導，不要求現有作業改架構，也不預先決定新 repo 必須用哪個 DB。共同提交以一次系統操作為範圍，不能開長交易等人工揀貨。

決策層目前建議仍需驗證的代價
業務責任／module先分清接單進度、揀貨確認、商品販售、庫存與買方資格；可以在同一較大 module 內分工。interface 要讓 caller 少懂 implementation，不是一個能力一個 Service／Impl。
交易送單的要求／受理／固定價／保留／去重同提交；後續回報或門市取消，各自保存結果與必要庫存變動。同一 DataSource／transaction manager、一致鎖序、正常結果與技術故障、JPA bulk update／快取都要驗。絕不跨人工等待持鎖。
部署與待辦新產品先以單一後端＋關聯式 DB 作候選，用持久紀錄保存待辦；人工操作不必由訊息 worker 驅動。app 重啟後待辦仍可見。前端／後端／E2E 同 repo 是版本管理方式，不等於同程序或必須一起部署；若將來跨服務，恢復另設計。
可選舊實驗，尚非新流程 spec

人工跨步驟，不等於跨服務取消

地圖保留 Reservation 身分、持久化取消工作、lease 與重啟接續的跨交易練習。這是刻意拿掉某次操作內共同 commit 的額外實驗，本地版不需要為同庫人工取消先建立 worker。

舊取消切片沒有完整涵蓋送單去重、人工供應確認、逐項解除保留或 create UNKNOWN。只用整筆 HELD → CANCELLED 也不能宣稱已支援新流程；門市取消權限、已揀商品與 Active Order 關係都要重看。

若將來兩條都做，先固定相同業務承諾與操作完成點，再比較故障恢復與效能。不拿功能較少的取消實驗與完整人工流程直接比 TPS 或 class 數。

帳面保留、實體商品與併發，各自守住什麼

買方不改單／取消，確實減少分支；送單去重、門市重複回報、取消競爭與庫存差異仍是需要處理的真實問題。

要守住的事建議守門不能當成保證的做法
同次送單不重複保留具範圍的唯一身分與交易協調，受理結果與保留同存；重試不重算第一次判斷。相同 payload 猜重複、記憶體 Set、先記做過再另存要求；constraint 失敗後仍在原失敗交易繼續。
送單價格固定送單短交易內以一致鎖／版本保護可售與價格核對，保存本次名稱／單價；後續只用已保存單價。交易外看過價就當保證、信任前端任意價、揀貨時才回查現價。保護的是短交易，不是鎖住商品直到揀貨結束。
帳面數量不重複分配條件更新、非負約束、保留歸屬驗證；多商品 writer 用一致順序，帳面不足回正常結果。先查夠再無條件寫、單程序鎖，或宣稱 DB 沒超額保留就證明現場一定有貨。
供應確認只做一次保護同份處理紀錄與逐項結果，回報與必要保留變動同提交；只接受符合流程與授權的操作。重複點按就多解除一次、任意填供應量繞過全量規則、直接讓 caller 改 status。具體操作粒度尚待定。
門市確認與整筆取消競爭依可取消階段，用鎖或經驗證的 CAS 排定結果；只解除當下仍有效的保留。各自先釋放再比版本，或確認覆蓋取消後又復活。買方無取消權也不能消除門市之間的競爭。
買方停用與新要求先補 Active Order 對新階段的定義；送單與停用遵守相同買方列守門。只在 READ COMMITTED 內查 exists、只靠 FK、期待建單自動推進 Account.version；把所有歷史紀錄都算活躍。
等待有界HTTP 在途、連線與鎖等待有上限；人工待辦持久化。技術暫時失敗必要時重試該次完整短交易。Virtual Threads 等於無限容量、開交易等人、只重試某條 SQL、HTTP timeout 就釋放已提交保留。
原公式不再適用

解除保留不等於補貨，Order 存在也不等於仍持有原數量

一份要求可能有商品送單就被排除、待揀後才不供應，或因門市取消而解除保留；原始行仍需留下。因此不能再用「所有尚未 Cancel 的 Order Lines 數量」直接當 reserved。

需要對帳的是：
  庫存保留總量 = 各購買要求目前仍有效的保留量總和

不再可直接套用：
  reserved = 所有尚未取消 Order Lines 的原始要求量總和

解除某項保留 ≠ 增加現場實際存量
帳面保留成功 ≠ 門市已備齊
原始購買要求 ≠ 最後供應內容
原受理結果 ≠ 目前處理進度

例：保留牛奶 5 瓶，門市發現只有 4 瓶，整項不供應。除了解除該項保留，還有帳面差異與可能已拿出商品的處理；不能只加回可售量就宣稱已對帳。具體校正、回架與再次可售規則仍待定，實作這條路徑前要補齊。

有效保留可以先由接單資料表達，不必先複製一套 Reservation Lines；若獨立庫存所有權或稽核真的需要 ledger 再評估。供應確認後保留如何結束也尚未定，本頁不假造完整庫存生命週期。

新產品與既有作業規則不同

停止新銷售，既有要求仍能處理

現有 Product 的 DELETED／SQLRestriction 同時影響查詢與庫存更新。只刪掉 reserved 大於零的下架檢查，release 仍可能更新零列；新需求必須拆開「能否接新要求」與「既有保留是否仍可操作」。不能全面拿掉過濾讓所有 caller 隨意存取。

歷史與待揀價格讀送單快照，不回查目前可售商品。這也解除改價改寫舊總額、下架缺商品造成 NPE 的根本依賴。取消、缺貨與已終止紀錄如何對授權 caller 可見，需在新契約明訂。

新產品不預設移入既有作業資料。若日後真的要匯入，未知歷史價格不能用現價假造，舊 reserved 也需另行核對；共同交易不會修好舊帳。現在沒有資料搬遷、清庫或執行 migration 的授權。

本地版仍要做對

Spring 交易接線與 JPA 快取

  • 每次系統操作由 Spring proxy 能攔截的 use-case 方法啟動 DB-only 短交易，內部以 REQUIRED 參與；REQUIRES_NEW 會拆成部分提交，自呼叫可能繞過代理。
  • save／flush 不等於最終 commit。成功回應等提交完成；commit 結果不明時先查同次操作紀錄，不盲目反向操作庫存。
  • 批次 UPDATE 不自動執行 auditing listener 或更新 managed entity；明確維護時間／版本，避免後來 flush 舊值蓋掉庫存。
  • 先定送單身分、買方、處理紀錄與商品／庫存的共同鎖序。送單、門市回報、整筆取消與管理 writer 都須遵守；悲觀等待與樂觀衝突都要量。
  • HTTP、寄信與人工揀貨都不放進持鎖交易。已拿出的商品不能靠 rollback 回架，實體作業與資料提交要分清楚。

能收多少要求，與能完成多少供應，分開量

接單很快但待辦一直堆積，不代表整個服務有同等供應能力。第一版沒有自動到期，更要看見待辦數、等待時間與占住的保留量。

已確認方向

固定環境，一般流量與熱門商品競爭分開測

  • 記錄 app／DB／壓測端資源、版本、instance 數、資料量與索引，說清楚壓測端是否已成瓶頸。用有限、可重複資料起跑。
  • 一般情境包含瀏覽、送單、查受理／目前進度，以及門市回報與取消；比例之後再定，不加入不存在的買方取消流量。
  • 熱門商品驗帳面保留競爭，不是公平秒殺隊列。補貨、回報不供應、取消或每輪重置須明確；不測到後半段全不足還混稱接單容量。
  • 逐段增加到達流量，量吞吐、p95／p99、拒絕、技術錯誤及 DB 連線／鎖等待；過載後再降載驗恢復。
  • 若用自動腳本模擬門市回報，清楚標示是系統測試，不當成人員真實揀貨速度或現場備貨能力。
分開計數要避免的誤讀
HTTP 到達、受理、過載拒絕、在途量未受理不是缺貨；timeout 不證明沒有保存，也不能釋放已提交保留。
新要求、進待揀／被排除商品、保留件數初次受理不是最終供應；全部被排除的快速結果不能灌成大量成功備貨。
同次重播與新受理大量重播很快，不代表能以相同速率接受新要求；核對沒有多筆要求或重複保留。
待辦數、最久／分布等待時間、保留量HTTP 回應再快，仍可能把人工流程壓垮。業務待辦上限與超限行為要另定。
供應確認量、未供應量、門市整筆取消不要混進送單吞吐；帳面不足與現場找不到也應分辨。
各操作延遲與正確性不以大量讀取稀釋送單／回報尾端延遲；有效保留、非負計數與解除只一次，逐階段核對。

目前沒有可宣稱的容量數字。Virtual Threads 讓等待執行緒便宜，Hikari、熱門資料列與門市人力仍有限；任何改善都要用明確負載與正確性基準證明。

新產品可以不同，既有作業不必跟著重寫

既有實作與上下游 CI 保留學習價值。下表談新產品可借用的經驗與不同選擇，不是要把現 repo 的 loopback、容錯或測試鏈路拆掉。

機制建議原因與條件
MVC／Validation、RFC 9457／ErrorCode保留基礎外部 HTTP 仍需驗證、穩定錯誤碼與遮蔽；正常未進待揀或不供應，用逐項結果表達，不一律丟整體例外。
PageResponse／CreatedResponse／DTO重訂送單與進度契約有名字的回應、分頁與 Location 原則有用；只有 id 不足以說明受理與供應差異，其他建立端點不必一併改。
JPA／Oracle／Flyway、Clock／audit可沿用真 DB、約束與可追溯 schema 有用。不要求換 ORM，也不能改已套用 migration 來逃避資料演化。
loopback Client／HTTP 池／內部 DTO既有保留，新案按需目前作業保留 HTTP 呼叫與教材價值。新產品同程序可以直接呼叫業務方法，不必先複製自呼叫、傳輸 DTO 與補償；不是來源 SpringBoot 的刪除工作。
嚴格遠端錯誤翻譯／HTTP 測試有真遠端時用本地不必先序列化再解析例外；獨立教材或外部依賴仍需明確 timeout、分類與冪等。
去重與持久進度本版必要固定初次受理答案，也能讀後續進度。全部未進待揀、全部不供應與取消都保留紀錄，scope／期限／wire 仍需定。
門市待辦先做人工流程保存待辦、供應回報與門市整筆取消；不先加複雜認領、掃描、通知或配送。這些不是一個長 DB 交易。
反向補償／取消 worker／MQ新案不先複製既有補償留作學習；新產品同庫的一次操作可共同提交，人工等待用持久進度。跨服務恢復可另做實驗，不因多階段就必須上 MQ。
自動到期 worker延後先人工處理與取消；未處理持續占量的代價要可見，未來有需求再定期限與競爭規則。
Resilience4j、Virtual Threads 與 DB 池新案依量測選用現作業的容錯配置保留；新產品依真遠端與有限資源選保護，不照搬每個 Service 的 breaker。現額度是 per-process 方法群，不是全叢集／每買方配額。
狀態、軟刪與可售過濾新案另定生命週期待揀與供應確認不能只靠 DELETED 表達；新產品按自己的流程定狀態與可見性，不機械複製舊 status，也不因此改寫既有作業 ADR。
安全買方與門市操作分開買方無自行取消權要在後端落實，門市操作另授權。Basic＋noop 是機器帳號 demo，非人類登入方案；Alloy 仍可能用 internal scraper 憑證。
觀測與本機堆疊訊號與後端分開選保留 health、log、必要 metrics，加入受理／保留／待辦／供應的分別計數；本機 Alloy／Prometheus／Tempo／Grafana 可選擇性跑。
既有上下游 CI原樣保留定位來源 SpringBoot 與獨立 Playwright repo 的測試／映像／下游驗證鏈路，是完整作業的一部分。新產品需求不觸發它們的淘汰或搬遷。
新案前端與 Playwright E2E同 repo，分階段加入第一階段只有可執行後端；稍後只取Playwright骨架、不搬舊案例，前端等實際需求再選框架與加入。新畫面／E2E與後端同版演進，但完整E2E、監控容器與前端不作開工前置。詳見工程階段。
測試與架構驗證經驗新案參考，不搬整套真 DB 驗鎖與提交、wire 驗契約、Playwright 驗完整操作。若有前端，還要驗真實畫面流程，不只 REST 測試。ArchUnit／Spring Modulith 有需要再加。
維運

先問要看出什麼問題

延續從需求反推監控：慢在送單還是回報、拒絕因過載還是帳面不足、門市待辦是否堆積、哪些保留一直未結束。不要只因有 metric 就放 panel。

本機教學堆疊與 app 匯出層分開；正式公開仍需 TLS、secret、管理權限與告警。本文不是完成正式部署的保證。

授權

不能只靠 body 的買方 ID 或畫面按鈕

現有 API Credential 與業務 Account 不同；caller 不能只帶 accountId 就查別人的要求，也不能自稱門市就回報供應或取消。

不必本輪加登入系統，但下一份契約要定義代表誰送單、查詢與門市作業的權限。可參考外部 IdP 遷移說明，單體／分散式不會自動解決。

先有可執行後端，再長出新產品流程

工程起點見分階段起跑手冊：沿用既有後端建置／測試，不必重做技術基礎，也不用先有Playwright、監控容器或前端。下列是後續業務依賴順序，不是第一個里程碑一次全做。

建議依賴順序

可信受理 → 人工確認 → 庫存收尾 → 容量 → 額外實驗

  1. 在已確認的pxgo-clone先交後端基礎

    依工程起跑清單分階段，不重問是否開repo。進入第一段送單用例前再定身分、授權與HTTP形狀；進入門市確認前補回報、取消、差異與Active Order規則。不預設搬舊資料，也不一次實作完整產品。

  2. 建立可信的送單與保留

    原始要求、逐項受理結果、送單價格／名稱、有效保留與去重一起設計。帳面不足整項排除；參考舊經驗，但不整套複製，也不沿用現價讀歷史內容的模型。

  3. 跑通最小人工流程

    待辦重啟仍可見；人員回報全量供應或整項不供應，買方查得到進度；門市依權限整筆取消。沒有買方自行取消窗口，也不先加自動到期。

  4. 驗庫存與競態

    缺貨／取消只解除有效保留一次，停售後仍能處理；固定價、回報／取消競爭、停用競爭與當次技術失敗 rollback。盤點、回架、確認後保留的規則先定再驗。

  5. 建立容量基準，再選額外實驗

    有限庫存、一般／熱點、受控過載與降載恢復；送單能力和供應完成分開量。想學 HTTP 故障或跨服務取消再另做，不是所有內部 module 的必選架構。

流程之後可以改，不代表現在就做兩套 runtime flags，讓同 schema 混跑互斥 writer。先保存原始事實與清楚的資料演化方式，讓修改有依據；不拿一條取消成功宣稱整個流程已可靠。

既有程式的學習分析與另案設計參考，放在Module 地圖的交接。那是經驗與差異對照，不是要求來源 SpringBoot 或下游依表遷移。

既有作業的學習依據，與新產品的差異

以下沿用來源SpringBoot 6f6218c的程式核對，說明可參考經驗與模型差異，不是pxgo-clone已實作內容。來源正式文件維持原案效力；新產品在自己的repo記錄spec／語言／ADR，不回頭覆寫來源規範。

現況定位／新需求落差
建立請求沒有確認價／送單身分CreateOrderRequest、CreateOrderLineRequest只有買方、商品、數量。需表達原要求、確認價與一次意圖，不只多加一個欄位。
成功只有 id，沒有人工處理進度OrderController:44–55、CreatedResponse、OrderTransactionalService:38–62不足以區分受理、待揀與最終供應。Order 建立時機與新操作契約另定。
沒有送單名稱／單價快照OrderLine:60–64、OrderService 讀取仍用當前 Product，缺商品可能 NPE；新流程要固定送單價格，也要保留未供應的原要求。
下架與庫存可操作性綁一起Product、ProductRepository、ProductService需讓既有保留在下架後仍可處理，不只刪檢查。
多商品不足即例外，庫存先獨立提交applyStockDelta與OrderService 寫入需分正常逐項結果與當次技術故障；舊買方改單／取消路徑也不能原封保留。
停用跨多次交易問有無單AccountLifecycleService:60–73先查再改，不等於並發安全。新流程還須補哪些階段算 Active Order。
正式詞彙與終止決策屬於既有作業CONTEXT的 Reservation／Delist／更新語意維持現案效力，不因新產品就改寫。ADR 0001的歷史保留理由可借鏡；ADR 0002也保留新增業務狀態的空間。新產品須按自己的流程另定語言、可見性與決策。
可以沿用的基礎build.gradle、RestClientConfig、BaseIntegrationTest、現行架構指引、測試規範、監控分層。只取需要部分，不順便改依賴／部署。
