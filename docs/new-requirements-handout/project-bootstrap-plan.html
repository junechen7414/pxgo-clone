最容易在沿用時漏掉的接線

這些是讀來源可確認的限制，不是本輪已在新專案修好的問題；第一階段實作時須逐項處理。

位置／風險起跑時的處理
原 docker-compose.yml把 app 與監控綁一起app 的 depends_on 含 alloy、ALLOY_HOST 指向它，還有固定 container_name／port。第一階段優先新建只有隔離 Oracle 的最小 Compose，後端從 IDE／bootRun 執行；若要容器 app，另外移除新專案對監控的啟動依賴，不整份照抄。
不跑監控，不等於自動不匯出來源 dev profile 有 tracing endpoint，預設 OTLP_TRACING_ENABLED=true。第一階段的新本地設定關閉 tracing 匯出或不設 endpoint；OTLP metrics 維持 false，保留 health／log／需要的本機 metrics 即可。不能光關容器卻讓 app 一直報連線失敗。
來源 init script 會印出生成的 SQL01_setup.sh將帳密代入 SQL 後輸出檔案內容；template也帶寬鬆的 ANY TABLE 權限。新專案不要原樣採用；改用不記錄秘密、僅限新 schema 的初始化方式，再單獨驗證。
.env 與 bootRun／IDE 是兩條路Compose 讀 .env 不代表 Spring Boot 或 IDE 會自動載入它。新 README 說明 env 如何進到後端程序；只提交 .env.example 占位值。不得把來源 .env、secret、個人本機工具設定或認證快取放進新 repo。
DB、volume、host port 與容器名稱新舊專案資料與容器資源分開；移除固定名稱或用新名稱、新 volume。若同時跑，主機 1521／8787 等 port 不能撞。新 datasource 與測試只能指到新資源，不共用舊作業帳密或 Flyway history。
已發布的舊 app 與新 E2E 可能版本不符同 repo 的驗證要啟動這次 commit 的後端，不直接拉舊 SpringBoot image／latest。E2E 日後啟用時將 base URL、spec、資料來源都對準本次版本。
映像建置與 HEALTHCHECK來源 Dockerfile可在需要容器 app 時借用；backend/ context、port、profile 與探針一起改。新 app 的 health 應反映 DB 就緒；本機 Podman 發布含 HEALTHCHECK 的映像要注意 Docker 格式。舊映像的探針契約不因新案而修改。
OpenAPI 型別與文件生成有穩定 API 才加入生成流程；從這次啟動的 app 取 spec，不能抓殘留 8787 舊 app 或用舊 Swagger 快照。H2 文件 profile 不是 Oracle 交易驗證，不拿文件生成成功代表業務測試通過。

來源 Playwright 檔案值得帶走的部分帶入前必須調整
package.jsonESM、pnpm、一般檢查／測試指令的組織。改專案名，只加有使用的依賴；不帶舊測試路徑、compose-restart、spec 同步與 CI 串接 scripts。舊 clean 是 Windows CMD 語法，不當跨平台方案；選定新 manifest 後產生自己的 lockfile。
playwright.config.tstimeout、reporter、失敗證據與 CI／本機輸出安排。移除 ui-setup／ui-staging／springboot-api 的舊 testMatch、dependencies、外站 URL 與預設 Basic header。只定義新專案已存在的 project；重定義 base URL、平行數與 retries，不用重試掩蓋失敗。
tsconfig.json、biome.json型別檢查、可讀 import、格式與 noFloatingPromises 等規則。依 e2e/ 新位置改 aliases／include，刪不存在的 pages／components 與舊 global setup；對齊 Node runtime、TypeScript preset、Node types 與 Biome schema。先選同一套，不混用來源不同 Node 主版本的宣告。
services/apis/base-api-client.tsApiRequester組合 request context、ApiResult<T>與狀態／錯誤斷言思路；它沒有依賴舊 generated schema。其中 CreatedResponse、正整數 id／Location、錯誤 code／detail／errors 與純文字自動轉數字，仍是契約假設，依新 API 留用。TypeScript 的 as T不是 runtime 驗證。
services/config/env.ts集中讀設定與驗證的入口。來源 env.ts 的 API_BASE_URL／8080 與 config 的 BASE_URL／8787 不一致，新案統一一個來源；不能假設這兩檔會自動讀 .env，缺必要值應明確失敗。
services/schema/common-types.ts手寫共用型別與生成型別分開的方式。分頁欄位與零起算等仍是新契約選擇；相符才留，不把舊型別當產品需求。
