本頁名詞與判定怎麼看
module／interface
module有interface與implementation；interface是caller正確使用它需知道的規則、時序、錯誤和成本，不只是Java方法清單。
depth／Locality
少量interface能使用很多行為；同一條知識集中修改與驗證。不是class越長越深，也不是DTO短就多餘。
deletion test
想像刪掉一層，複雜度消失還是散回caller？用來檢查價值，不是以刪class數量評分。
送單快照／讀取快照
前者長期保存通過送單核對的商品名稱／價格；後者只是交易內把lazy資料抄成普通物件，避免session外再載入。兩者都不能代替買方原始要求或後續供應結果。
原始要求／受理結果
前者保存買方要什麼、要多少與確認價；後者保存第一次送單的逐項判斷、排除原因、固定價格與保留量，包含全未進待揀。同次重試不重算。
揀貨／供應與進度
門市人工確認能否備齊同商品的完整要求量，不足整項不供應。後續供應結果與目前進度另存、可查，不覆寫歷史受理結果，也不刪掉未供應的原需求。Order建立時點、待處理身分與狀態名仍待定。
仍有效保留
送單先保留帳面量，不保證現場足貨；不供應或門市整筆取消只解除該項仍有效保留。解除不等於補貨、盤點修正或已拿出的貨已回架；供應確認後的庫存去向仍待議。
冪等／穩定身分
同一次意圖重送不重建、不再保留、不重算首次判斷；不是用payload相同猜重複。scope、異內容衝突、期限與POST重播／進度查詢wire契約仍待定。
人工待辦／HTTP在途
已受理待揀要求要持久化、重啟可見；HTTP同時處理量與等待另設界線。人工待辦不等於MQ，是否限制業務待辦數仍待定。
可選跨交易實驗
舊取消實驗用ledger記持有者、outbox記待送意圖、lease／token擋舊worker回寫、tombstone擋遲到操作復活。它尚未涵蓋逐商品供應；本地人工流程不因此必須採用這套機制。

已確認業務

送單確認價格，揀貨確認供應

  • 單一自營商家，以門市型即時購物作產品參考；不宣稱外部業者實際制度已查證，不使用其品牌或標誌。第一版延伸到人工揀貨／供應確認，仍不含支付（含模擬）、配送、退款、替代商品等完整營運。
  • 送單核對買方確認價、可售條件與帳面可用量。通過的商品固定當次價格／名稱，保留完整要求量、等待人工揀貨；這是帳面保留，不保證現場足貨。異價、不可售或帳面不足的商品整項不進待揀、不先保留部分，其他商品獨立判斷。
  • 同商品必須備齊：要5件現場只有4件，整項不供應，不縮量；其他商品各別確認。未進待揀或未能供應者不自動候補、補單。門市回報不供應時，解除該項尚有效保留。
  • 等待期間改價不影響本次價格，供應確認不用現價重算。買方原始要求、逐項送單受理結果（排除原因／固定價格／保留量）、後續揀貨／供應結果與目前進度分開保存；不刪缺貨行來掩蓋原需求。
  • 同次重試不重建、不再保留、不重算第一次送單判斷。歷史受理結果固定，進度查詢另反映後續供應或門市取消；具體POST重播與查詢wire契約仍待定。全未進待揀、揀貨後全未供應都要留紀錄，Order何時建立與待處理身分尚未決定。
  • 送單成功後買方不能自行修改或取消，送單前須明確說明，不提供開始揀貨前的取消窗口。這是前一回合為「以定義規避例外」採用的分界。門市仍可人工整筆取消以解除保留，但適用時機、授權、原因與實體貨品處置尚未完整定案。
  • 第一版先做人工處理與門市整筆取消，不做自動到期；這是開發順序，不是永遠無期限的決定。待辦必須可見，無人處理會持續占量，不默加timeout自動釋放。
  • 解除保留不等於補貨或盤點修正；缺貨量解除後不能就宣稱帳面正確。對帳改看仍有效保留的逐項紀錄，不能再以所有未取消Order Lines總和代替，也不必先決定ledger。
  • 下架只停新銷售，不自動取消、不隱藏既有保留的操作及舊紀錄。買方有Active Order不可停用仍保留，但待揀、部分供應、全不供應、取消與供應完成哪些算Active Order，必須重新明定。
  • 仍推薦單app＋單Oracle。每個操作各用短本地交易：送單紀錄／去重／固定價／保留同提交；供應回報／保留變動或門市取消各同提交。交易或DB鎖不能跨人工等待，人員揀貨也不是DB rollback能撤回；不因人工流程就必上MQ、worker或微服務。
  • HTTP在途量與等待仍有界拒絕；已受理待揀要求必須持久化、重啟可見。是否另設業務待辦上限尚未定；效能分送單／保留吞吐與人工供應完成，不以前者當整個履約容量。

仍未定：HTTP與重播／查詢wire、idempotency scope／期限／衝突、Order建立與待處理身分、狀態名／表數及逐項回報或整批完成的操作粒度；門市授權與並行操作、整筆取消時機與原因；庫存差異校正、回架／再次可售、供應確認後持有／轉已售／完成與Active Order；舊資料採認、容量與待辦上限。見明確待議。同商品不足不縮量、送單固定價、先保留、人工揀貨與買方不可取消均已定案，不再列成問題。

以作業檔案對照新產品知識

下列是另案新產品的責任候選，不是批准修改來源SpringBoot的package／資料表／部署。既有作業原樣保留作教材；單app＋單Oracle是新產品候選，不是移轉回來源SpringBoot的命令。

現有知識位置新需求下的責任動作與不可漏的相依
Product名稱／價格／DELETED商品販售：現在賣什麼、按什麼權威價格、是否接受新送單。送單核對後固定名稱／價格，供應確認不用現價重算。與庫存可操作性分開；改價／下架競爭要守門，下架不自動取消、也不能藏起舊保留與操作。
Product.available／reserved、applyStockDelta庫存：帳面可用量、逐項有效保留與解除。保留條件UPDATE思想、整項不足結果與鎖序。只解除已證明仍有效的保留，不給任意caller傳數量多還；對帳不能再加總所有未取消Order Lines。解除與盤點修正／實體回架分開，供應後庫存去向待議，不先強制ledger。
OrderService建立／補償／讀產品送單受理、歷史結果重播，以及後續人工供應進度的協調。正常逐項排除／不供應與技術故障分開，不先抽共同補償。送單後買方不改不取消；門市整筆取消與逐商品供應不能只沿用舊delete流程。
CreatedResponse只有id、沒有送單紀錄原始要求與送單受理結果：固定的第一次判斷。全未進待揀也保存逐項原因；與去重、固定價、保留同提交。後續全不供應也留紀錄，不為結果再拆一個服務，不先斷定何時建立Order或要幾張表。
OrderLine只有productId／quantity；讀取查現價區分要求量、送單固定名稱／單價／保留量與後續供應結果。不以刪缺貨行或縮量覆蓋原需求；歷史讀取不查現價。已受理內容不是已保證供應，舊單未知價格不以現價假造，migration採認先定。
目前沒有對應的人工待辦／回報用例持久化待揀要求、人工供應結果與目前進度。同商品完整備齊才供應；不供應解除該項有效保留。待辦重啟可見，每次回報／取消各短交易，不跨等待持鎖；狀態名、操作粒度與並行授權待定，不因此預設MQ／worker。
Account資格、AccountLifecycleService的有單檢查買方資格／生命週期支援能力。保留有Active Order不可停用，集中協調避免循環。新進度如何計入Active Order待明定，不能只用尚未Cancel或由是否有Order列推定；不預設獨立會員module。
*Client與RestClientConfig、入口韌性設定傳輸與HTTP資源保護，不是業務責任本身。單app本地基準用Java呼叫；真跨交易才另設恢復。HTTP在途／等待有界，已受理人工待辦要持久化；待辦上限與人工完成容量另議，不用傳輸隊列取代業務紀錄。

以下HELD→CANCELLED與ledger是舊取消實驗的假設，不是本次核准的資料表或完整生命週期。它讓庫存責任擁有穩定Reservation身分與持有lines，計數與狀態在自己的短交易一致、與送單commit分開；本地基準不因此必須設ledger。

  • 同ID／同內容reserve不多保留，異內容衝突；已取消後不能讓遲到reserve復活。這是庫存操作去重，不等於整個送單歷史結果／POST重播契約。
  • 舊HELD取消只解除自己的lines並與狀態同提交，重複取消不改量；新流程還須逐項辨識仍有效保留，避免已不供應解除的項目再被整筆取消重還。這一段舊二態沒有解決。
  • 未知ID先取消留終止紀錄以擋遲到操作的概念可取用；所有權與門市授權不能只靠猜不到ID。原始要求與歷史受理也不能因保留終止就消失。
  • 同header競爭以鎖／唯一約束仲裁、商品鎖序一致的原則仍有效；缺必要列／計數不足rollback，不當冪等成功吞掉。但人工供應與門市取消並行的准入條件仍待設計。
  • 下架不影響保留操作存在性；終止與歷史不能被可售filter抹掉。保護紀錄的保留期限不同於業務保留自動到期，不能藉此默加timeout。
